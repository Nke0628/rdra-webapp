目的と背景

ゴール

  • G-01
    輸入した商品をタイムリーに紹介し、Web で顧客に直接販売する
    直営店での小売りに加え、はじめての通信販売を始める
  • G-02
    顧客と直接つながり、商品に対する顧客の声をダイレクトに把握して商品開発につなげる
    顧客のレビュー・感想を営業が集計して使う

初期要望

いちばん実現したいこと

輸入した商品をタイムリーに紹介し直接販売する。顧客と直接つながることで商品に対する顧客の声をダイレクトに把握し商品開発につなげる。

背景

ABC商事は輸入販売の商社で、従来は直営店を数十店持ち、そこで小売りを行っている。新たに Web を使った通信販売を始める。通信販売はこの会社にとってはじめて。システム部門が中心となり、関係部署へのヒアリングで要望をまとめる。関係する部署: 顧客、経営者、営業、オーダー部門、物流、システム部門経営者は売上の状況を見る。システム部門はこのシステムの利用者ではない(保守のみ)。関係する既存システム: 入荷システム、出荷システム、決済システム経営層は、営業にはオーダー作業よりも戦略的な商品管理の仕事にシフトしてもらいたい。オーダー処理は新たにオーダー部門を用意して集約する。営業は、多様な顧客のニーズに沿えるように入金手段を多くしてほしい。物流は、既存の入庫、出庫システムとの連動を望んでいる。入庫、出庫システムは入荷システム、出荷システムと同じもの。システム部門は、保守性を考え使用する技術を統一したい。決済システム: 入金情報を通知する(決済会社の決めたフォーマットで Web サービスを呼び出す)。出荷システム: 出荷指示を受け付け、出荷作業の完了を通知する。入荷システム: 入荷商品の情報を通知する。配送会社が配送終了をメールで通知する。在庫切れのときは取引先に対して発注する。取引先への発注(在庫切れ時の追加発注、新規商品の発注)はこのシステムで記録し、発注先への送付は従来どおりの手段で行う。物流の出荷は朝、昼、夕方の各3時間単位の締め毎に行う。商品の入荷は午後にまとめて送られてくる。

やらないこと

直営店での販売・店舗の在庫。直営店と Web の在庫は共有しない。配送会社とのシステム連携(配送終了はオーダー部門がメールを見て完了にする)。

アクターと外部システム

アクター

顧客

Web で商品を購入する人。会員登録しなくても購入できる

営業

取り扱い商品の登録・削除、売上の分析、品揃えの検討、新規商品の発注を行う

オーダー部門

オーダー処理を集約して行う(新設)。入金の確認、出荷指示、追加発注、返品の受付を行う

物流

出荷作業と入荷情報の入力を行う

経営者

売上の状況を見る

外部システム

決済システム

入金情報を通知する(決済会社の決めたフォーマットで Web サービスを呼び出す)

出荷システム

既存。出荷指示を受け付け、出荷作業の完了を通知する

入荷システム

既存。入荷商品の情報を通知する

要求

システムに求めることを「機能」「非機能」「方針」に分けています。

機能

システムでできること。画面で入力する、計算する、表示するなど

  • R-01
    顧客が Web で商品を選び、決済情報と送付先を入力して購入できる
    カートに追加してから購入指示を行う
  • R-02
    営業が仕入れた商品を Web の取り扱い商品として登録・削除できる
    輸入した商品をタイムリーに紹介する
  • R-03
    顧客がオーダー商品の現在の状態を確認できる
  • R-04
    顧客が会員登録できる。会員登録しなくても購入できる
  • R-05
    顧客が出荷前のオーダーを Web でキャンセルできる
  • R-06
    決済システムの入金情報通知を受けてオーダーと照合し、照合できないもの・金額が異なるものだけオーダー部門が確認する
  • R-07
    出荷指示の前にオーダー別の在庫を確認し、在庫切れのオーダーを入荷待ちにする
  • R-08
    入荷システムから送られる入荷情報で、入荷待ちのオーダーの入荷待ちを解除する
  • R-09
    入金が確認されたオーダーの出荷指示を、そのまま出荷システムへ連携する
  • R-10
    取引先への発注(在庫切れ時の追加発注、新規商品の発注)を記録する
    発注先への送付は従来どおりの手段で行う
  • R-11
    営業が商品の特性と売れた時期・売れた場所を管理し、売れた場所をマップ上に表示できる
    売れた場所は送付先の地域
  • R-12
    売上を週単位で集計し、月単位でも見られる
    営業が週単位で分析し、次週以降の品揃えを検討する
  • R-13
    購入した顧客が商品のレビュー・感想を Web で投稿できる
  • R-14
    営業が商品ごとにレビュー・感想を集計し、商品開発の検討に使える
  • R-15
    営業が、今後追加発注しない在庫商品をマークし、売れ筋商品の在庫量を多くできる
    在庫切れによる機会損失を無くす
  • R-16
    経営者が売上の状況を見られる
  • R-17
    多様な顧客のニーズに沿えるように、入金手段を多く用意する
  • R-21
    オーダーを受理したことと支払い方法を顧客にメールで通知する
  • R-24
    オーダー部門が配送会社からの配送終了のメール通知を確認し、オーダーを完了にできる
    配送会社とのシステム連携はしない

非機能

機能をどれだけ快適・安全に使えるか。速さ、使える端末、個人情報の守り方など

  • R-19
    保守性を考え、使用する技術を統一する

方針

システムの作り方ではなく、事業・運営として決めること。料金、だれ向けのサービスか、データをいつ消すか、制度改正への追従など

  • R-18
    オーダー処理は新たに用意するオーダー部門に集約し、営業は戦略的な商品管理の仕事にシフトする
  • R-20
    直営店と Web の在庫は共有しない。直営店での販売・店舗の在庫は対象外
  • R-22
    入金額が不足する場合は差額の追加支払いを依頼し、多すぎる場合は差額を返金する
    オーダー部門が顧客にメール・電話で確認する
  • R-23
    返品はオーダー部門がメールもしくは電話で受け付ける
  • R-25
    出荷は朝・昼・夕方の各3時間単位の締め毎に行う

  • Q-001「顧客の声を把握し商品開発につなげる」は、どの業務で実現しますか

  • Q-002顧客は会員登録してから購入しますか

    決済システムの入金情報通知を受けてシステムがオーダーと照合し、照合できないもの・金額が異なるものだけオーダー部門が確認する
  • Q-004出荷指示は誰がどこへ出しますか(オーダー部門と物流の役割)

  • Q-005取引先への発注は、このシステムで扱いますか。誰が行いますか
    在庫切れ時の追加発注(物流)も新規商品の発注(営業)もこのシステムで記録し、発注先への送付は従来どおりの手段で行う
  • Q-006直営店での小売りは、このシステムの対象外ですか
    直営店での販売・店舗の在庫は対象外。直営店と Web の在庫は共有しない
  • Q-007経営者とシステム部門は、このシステムを使いますか
    経営者は売上の状況を見る。システム部門は利用者ではない(保守のみ)
  • Q-008売れた時期は、月単位と週単位のどちらで管理しますか
    週単位で集計し、月単位でも見られるようにする
  • Q-009「売れた場所」は何の場所ですか
    顧客が入力した送付先の地域(都道府県・市区町村)
  • Q-010物流の言う「入庫、出庫システム」は、「入荷システム、出荷システム」と同じものですか
    同じもの
  • Q-011オーダーのキャンセルや返品は受け付けますか
    出荷前のキャンセルを顧客が Web で行え、返品はオーダー部門がメール・電話で受け付ける
  • Q-012このシステムの名前を決めてください
    rdra-webapp

  • Q-014配送会社からの配送終了の連絡は、人がメールを見て処理しますか

    出荷指示の前に、システムがオーダー別の在庫を確認して在庫切れのオーダーを入荷待ちにし、オーダー部門が取引先に追加発注する

    その他 → (チャットでの指示)業務の単位がおかしい。オーダー業務の一連の流れとして「Webでの購入 → オーダー → 出荷」があるはず
  • Q-018営業の商品管理を、商品1件ごとの仕事と、週ごとにまとめて行う仕事の2つの業務に分けてよいですか
    (1) 業務「商品管理」(商品1件ごと): 「取り扱い商品を登録・削除する」「追加発注しない在庫商品をマークする」「売れ筋商品の在庫量を多くする」。(2) 業務「商品企画」(週ごと): 流れ「週単位で売上を分析し品揃えを検討する」に、売上の集計(週・月)、売れた場所のマップ表示、場所と商品の特性での分析、品揃えの検討をまとめる。「新規商品を発注する」は発注の業務に移す
  • Q-019オーダー部門の仕事を、次の流れにまとめてよいですか
    その他 → (チャットでの指示)オーダー業務の一連の流れとして「Webでの購入 → オーダー → 出荷」があるはず。受理〜出荷指示〜完了は、顧客の購入・物流の出荷と合わせて1つの流れにする
  • Q-020商品ごとの在庫数は、このシステムで持ちますか。入荷システム・出荷システムの在庫を参照しますか
    このシステムが Web 用の在庫数を持ち、入荷システムの入荷情報で増やし、出荷システムの出荷完了で減らす
  • Q-027入荷した商品は、取引先への発注と突き合わせますか
    Q-035 の回答(A: 発注と入荷の突き合わせを発注業務にまとめる)により確定
  • Q-032物流の出荷作業を、オーダーの流れから外して別の業務「出荷業務」にしてよいですか
    物流の「締め毎に出荷作業を行う」と、出荷システムの「出荷作業の完了を通知する」を、業務「出荷業務」の流れ「締め毎に出荷する」にする。オーダーの流れは出荷指示まで。出荷完了の通知を受けてオーダーは「出荷済」になる。出荷指示は「指示済」→「出荷済」と進む
  • Q-033「Webで注文された商品を届ける」を、待ちが入るところで次の5つの流れに分けてよいですか
    (1)「注文を受け付ける」(顧客が商品を選ぶ・カートに追加する・購入指示を行う・決済情報と送付先を入力する → 受付済)、(2)「オーダーを受理する」(オーダー部門がオーダーを確認し、受理と支払い方法をメールで通知する → 入金待ち)、(3)「入金を確認して出荷を指示する」(顧客がメールを見て支払う → 決済システムの入金通知をオーダーと照合する → 在庫を確認する → 出荷を指示する。在庫切れなら入荷待ちにする)、(4)「入荷したオーダーの出荷を指示する」(入荷システムの入荷情報で入荷待ちを解除し、出荷を指示する)、(5)「配送終了を確認してオーダーを完了する」(配送会社のメールを確認し、オーダーを完了する)。顧客の「オーダーの状態を確認する」はオーダーを進めないので、(1)の中の作業として置く
  • Q-034照合できない入金の確認から差額の精算までを、1つの例外の流れ「入金差異を解消する」にまとめてよいですか
    照合できない入金・金額の違う入金をオーダー部門が確認し、顧客と差額を確認して、不足分の追加支払いを依頼するか過多分を返金するまでを、流れ「入金差異を解消する」にする。差異のあるオーダーは「入金差異あり」にし、解消したら入金確認済に進める
  • Q-035取引先への発注と入荷の突き合わせを、1つの業務「発注業務」にまとめてよいですか
    業務「発注業務」に、流れ「在庫切れの商品を追加発注する」(オーダー部門)、「新規商品を発注する」(営業)、「入荷を発注と突き合わせる」(物流の入荷情報の入力 → 入荷システムからの入荷情報を発注と突き合わせ、発注を入荷済にする)を置く。入荷待ちの解除はオーダーの流れに移す

理由
Q-034 で「解消したら入金確認済に進める」と決まったが、その後にどの作業へ進むかの記述がない。業務フローで先・次をつなぐと、解消の後の行き先が決まらない
  1. A 提案どおり(解消したら在庫の確認に進む)
  2. B 不足分は、顧客が追加で支払ったあと決済システムの入金通知で照合し直す(入金の照合に戻る)
  3. C 差額が解消できないときは、オーダーをキャンセルする流れも入れる
  4. D その他 → ___

  • BUC:入金差異を解消する/不足分の追加支払いを依頼する
  • BUC:入金差異を解消する/過多分を返金する
  • BUC:返品を受け付ける/返品された代金を返金する
  • BUC:返品を受け付ける/返品された商品を在庫に戻す
  • BUC:売上の状況を見る/売上の状況を見る
