# システム名
rdra-webapp［回答:Q-012］


# 最重要要求
輸入した商品をタイムリーに紹介し直接販売する。［資料:メモ2.txt システムの目的］
顧客と直接つながることで商品に対する顧客の声をダイレクトに把握し商品開発につなげる。［資料:メモ2.txt システムの目的］


# 背景
ABC商事は輸入販売の商社で、従来は直営店を数十店持ち、そこで小売りを行っている。［資料:メモ1.txt］
新たに Web を使った通信販売を始める。通信販売はこの会社にとってはじめて。［資料:メモ1.txt］
システム部門が中心となり、関係部署へのヒアリングで要望をまとめる。［資料:メモ1.txt］
関係する部署: 顧客、経営者、営業、オーダー部門、物流、システム部門［資料:メモ2.txt 部署の想定］
経営者は売上の状況を見る。システム部門はこのシステムの利用者ではない(保守のみ)。［回答:Q-007］
関係する既存システム: 入荷システム、出荷システム、決済システム［資料:メモ2.txt 既存システム］
経営層は、営業にはオーダー作業よりも戦略的な商品管理の仕事にシフトしてもらいたい。オーダー処理は新たにオーダー部門を用意して集約する。［資料:メモ3.txt 経営層］
営業は、多様な顧客のニーズに沿えるように入金手段を多くしてほしい。［資料:メモ3.txt 営業］
物流は、既存の入庫、出庫システムとの連動を望んでいる。［資料:メモ3.txt 物流］入庫、出庫システムは入荷システム、出荷システムと同じもの。［回答:Q-010］
システム部門は、保守性を考え使用する技術を統一したい。［資料:メモ3.txt システム部門］
決済システム: 入金情報を通知する(決済会社の決めたフォーマットで Web サービスを呼び出す)。［資料:メモ4.txt 外部システム仕様］
出荷システム: 出荷指示を受け付け、出荷作業の完了を通知する。［資料:メモ4.txt 外部システム仕様］
入荷システム: 入荷商品の情報を通知する。［資料:メモ4.txt 外部システム仕様］
配送会社が配送終了をメールで通知する。［資料:メモ4.txt オーダー部門］
在庫切れのときは取引先に対して発注する。［資料:メモ4.txt 物流］
取引先への発注(在庫切れ時の追加発注、新規商品の発注)はこのシステムで記録し、発注先への送付は従来どおりの手段で行う。［回答:Q-005］
物流の出荷は朝、昼、夕方の各3時間単位の締め毎に行う。商品の入荷は午後にまとめて送られてくる。［資料:メモ4.txt 物流］


# 業務の概要
・Webでの商品購入(顧客)［資料:メモ4.txt 顧客］
  - 購入する商品を選びカートに追加する［資料:メモ4.txt 顧客］
  - 商品を選び終えた後で購入指示を行い、決済情報と送付先の情報を入力する［資料:メモ4.txt 顧客］
  - ABC商事からのメールを確認し、記載された金額を Web で選択した決済方法に従って支払う［資料:メモ4.txt 顧客］
  - オーダー商品の現在の状態を確認する［資料:メモ4.txt 顧客］
  - 会員登録する(会員登録しなくても購入できる)［回答:Q-002］
  - 出荷前のオーダーを Web でキャンセルする［回答:Q-011］
・商品管理(営業)［資料:メモ3.txt 営業、メモ4.txt 営業］
  - 仕入れた商品を Web 上での取り扱い商品として登録、もしくは削除する［資料:メモ4.txt 営業］
  - 商品の特性と売れた時期、売れた場所を管理する。売れた場所はマップ上に表示する［資料:メモ3.txt 営業］売れた場所は送付先の地域とする［回答:Q-009］
  - 週単位でその週の売り上げ情報を分析(場所と商品の特性)し、次週以降の商品の品揃えを検討する［資料:メモ4.txt 営業］
  - 在庫商品について、今後追加発注しないものをマークする［資料:メモ4.txt 営業］
  - 売れ筋商品で在庫切れによる機会損失を無くすために在庫量を多くする［資料:メモ4.txt 営業］
  - 新規商品を販売する場合に発注する［資料:メモ4.txt 営業］
・オーダー処理(オーダー部門)［資料:メモ3.txt 経営層、メモ4.txt オーダー部門］
  - オーダー確認を行い、オーダーを受理したことと支払い方法を顧客にメールで通知する［資料:メモ4.txt オーダー部門］
  - 決済システムの入金情報通知を受けてシステムがオーダーと照合し、照合できないもの・金額が異なるものだけオーダー部門が入金確認を行う［回答:Q-003］
  - 出荷指示の前に、システムがオーダー別の在庫を確認し、在庫切れのオーダーを入荷待ちにする［回答:Q-015］
  - 在庫切れのとき、取引先に追加発注する［回答:Q-015］
  - 入金が確認されたオーダーの出荷指示を行い、出荷指示はそのまま出荷システムへ連携される［資料:メモ4.txt オーダー部門］［回答:Q-004］
  - 入金額が異なる場合は、顧客とメールもしくは電話で差額を確認し、差額の追加支払いを依頼する［資料:メモ4.txt オーダー部門］
  - 入金額が多すぎた場合は、顧客に連絡し差額を返金する［回答:Q-013］
  - 返品をメールもしくは電話で受け付ける［回答:Q-011］
  - 配送会社による配送終了のメール通知を確認し、対応するオーダーを完了する［資料:メモ4.txt オーダー部門］［回答:Q-014］
・出荷と入荷(物流)［資料:メモ4.txt 物流］
  - 締め毎に商品を出荷する(物流は出荷作業のみを行う)［資料:メモ4.txt 物流］［回答:Q-004］
  - 入荷情報を入荷システムに入力する。その情報は入荷システムから当システムに送られ、当システムは入荷待ちになっているオーダーの入荷待ちを解除する［資料:メモ4.txt 物流］
・顧客の声の把握［資料:メモ2.txt システムの目的］
  - 購入した顧客が商品のレビュー・感想を Web で投稿する［回答:Q-001］
  - 営業が商品ごとにレビュー・感想を集計し、商品開発の検討に使う［回答:Q-001］


# スコープ外
直営店での販売・店舗の在庫。直営店と Web の在庫は共有しない。［回答:Q-006］
配送会社とのシステム連携(配送終了はオーダー部門がメールを見て完了にする)。［回答:Q-014］


# その他

# AIのメモ(採用時に消える)
- 最重要要求は会社の目的の形で書かれている。「だれが・何をできるようになるか」の形(例: 顧客が Web で直接商品を買える/営業が顧客の声を商品開発に使える)への書き直しは phase1 のゴール・要求で扱う。
- 「技術を統一したい」の統一の対象(既存システムと同じ技術か、社内標準か)は資料にない。phase1 以降の制約として確認する。
- 「オーダー部門のメール通知」「配送会社の配送終了メール」など、メールでのやりとりが多い。メール送信をシステムで自動化するかは phase2 で扱う。
- Q-004・Q-015 の回答で物流は出荷作業と入荷情報の入力のみとなり、メモ4の物流の「出荷指示」「在庫状況のチェック・入荷待ち・発注処理」は、オーダー部門とシステムの業務として書き直した。
- 背景の「在庫切れのときは取引先に対して発注する」(メモ4 物流)は、発注するのがオーダー部門になった(Q-015)。
- 経営者が売上の状況を見る業務(Q-007)は、業務の概要にはまだ置いていない。phase1 で営業の売上分析と合わせて扱う。
